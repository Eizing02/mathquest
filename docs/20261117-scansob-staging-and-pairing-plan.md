# แผนส่งต่อ: รับคะแนน ScanSob และขอเชื่อม MathQuest โดยไม่ใช้รหัส

> การเปิดใช้แบบล่าสุดไม่ต้องลงรายชื่ออีเมลล่วงหน้า ดู [คู่มืออนุมัติรายคำขอ](20261117-scansob-review-each-request.md) หลังสลับโหมดแล้วให้ยึดคู่มือนั้นสำหรับนโยบายการเปิดรับและปิดทางรหัสเดิม

**สถานะ: MathQuest ทำส่วนของตนในเครื่องแล้ว รอ ScanSob ยืนยันสัญญาและทดสอบร่วมกันบน staging · 17 พฤศจิกายน 2569**

เอกสารนี้ต่อจากใบงาน ScanSob วันที่ 17 พฤศจิกายน ดูชื่อไฟล์ SQL สองระยะ ตัวอย่าง ACK, error และค่าตั้งใน [Handoff ฝั่ง MathQuest ฉบับปรับตามแผน](20261116-scansob-code-free-pairing-handoff.md) งานที่ผ่านในเครื่องยังไม่ใช่หลักฐานเปิดใช้จริง

## 1. ผลที่ต้องการและขอบเขต

1. ครูเข้าระบบ **ScanSob ด้วยบัญชีของตน** เลือก Workspace ที่ตนมีสิทธิ์จัดการ เห็น MathQuest ปลายทาง ยืนยันขอบเขตการส่งคะแนน แล้วกด **ส่งคำขอเชื่อมต่อ** ไม่ต้องขอหรือพิมพ์รหัส
2. ผู้ดูแล MathQuest เห็นกระดิ่งพร้อมจำนวนคำขอค้างและแจ้งเตือนเมื่อมีคำขอใหม่ เปิดดูผู้ส่ง อีเมลที่ยืนยันแล้ว ชื่อและ ID ของ Workspace โรงเรียนปลายทาง และเวลาที่ส่ง แล้วกด **อนุมัติ** หรือ **ปฏิเสธ** ปิดแจ้งเตือนไม่เท่ากับปฏิเสธ
3. ScanSob แสดง **เชื่อมต่อแล้ว** หลังได้รับและบันทึกสิทธิ์สำเร็จเท่านั้น จากนั้นจึงกดส่ง **ผลสอบที่ยืนยันแล้ว** ตามโหมดเดิม การอนุมัติไม่ทำให้คะแนนเก่าถูกส่งหรือเปิดให้นักเรียนเห็นโดยอัตโนมัติ
4. ขอบเขตการเชื่อมต่อคือ `score:write` สำหรับ Workspace และปลายทางที่อนุมัติเท่านั้น **ไม่ใช่การเพิ่มบัญชีแอดมิน การให้รหัสล็อกอิน MathQuest หรือสิทธิ์อ่านทะเบียนนักเรียน**

### ครูต่างโรงเรียนใช้ได้เมื่อใด

- รุ่นแรกให้ส่งมายัง **MathQuest โรงเรียนเดียวที่ตั้งไว้** ครูต่างโรงเรียนส่งคำขอได้เมื่ออยู่ในรายชื่อที่ผู้ดูแลอนุญาตและรับผิดชอบสอบให้กับนักเรียนในทะเบียนโรงเรียนปลายทางจริง ตรวจความสัมพันธ์นี้ก่อนอนุมัติ Workspace ไม่ใช้ชื่อโรงเรียนที่พิมพ์ได้หรือโดเมนอีเมลอย่างเดียวเป็นหลักฐาน
- ถ้าครูต่างโรงเรียนจะส่งคะแนนนักเรียน **ของโรงเรียนตนเอง** อย่าส่งเข้าทะเบียน MathQuest ของเรา ตัวรับเดิมจับคู่ด้วยรหัส 5 หลัก รหัสที่เหมือนกันแต่คนละโรงเรียนอาจไปลงผิดคนได้ ควรใช้ปลายทาง MathQuest ของโรงเรียนนั้นที่แยกข้อมูลจริง หรือออกแบบระบบหลายโรงเรียนก่อน ไม่รวมในรอบนี้
- รายชื่ออีเมลตั้งครั้งเดียวและปรับได้ ไม่ต้องส่งเลขหรือ ID ให้ครูกรอกเอง การเพิ่มชื่อในรายชื่อให้สิทธิ์ **ส่งคำขอ** ไม่ใช่ **อนุมัติอัตโนมัติ** ผู้ดูแลยังตรวจว่า Workspace ที่เลือกใช้ทะเบียนถูกชุดทุกครั้งที่มีการเชื่อมใหม่

## 2. งานระยะ A: ยืนยันการส่งคะแนนเดิมบน staging

| เจ้าของ | สิ่งที่ต้องทำ |
| --- | --- |
| **MathQuest** | ตรวจว่า staging ใช้ receiver profile 1.1, migration 03 และ Edge Function `ingest-scansob-results` กับ `pair-scansob-workspace` รุ่นที่เข้าคู่กัน เตรียมครูผู้ดูแลและนักเรียนจำลองแยกจาก Production เปิดรับเฉพาะการทดสอบที่อนุมัติแล้ว |
| **ScanSob** | ล็อก checkout ที่ใช้ทดสอบ ส่ง commit พร้อม `lib/integrations/mathquest/contract.ts` และ fixture จากชุดเดียวกัน ตรวจ staging ลง **020 → 021 → 022 → 023** ตามที่ขาด โดย SQL ชุดนี้รันเฉพาะ Supabase ของ ScanSob ตั้งปลายทางเป็น Supabase staging ของ MathQuest ใช้การจับคู่ด้วยรหัสเดิมและส่งแบบ manual ก่อน |
| **ร่วมกัน** | อย่างน้อยสอง Workspace และสองบัญชีนักเรียนจำลอง ทดสอบรหัสตรง 1 รายการและไม่พบ 1 รายการ จดผล ACK หลัง commit ทดสอบส่งซ้ำ หลาย batch สลับลำดับ เปิด/ปิดการดูคะแนนและสลับบัญชี แก้รหัสแล้วส่ง revision ใหม่ ถอนคะแนน และทดสอบภาคเรียนที่ปิด |

**เกณฑ์ผ่าน A:** ScanSob และ MathQuest เทียบยอดได้จาก Workspace + ข้อสอบ + revision เดียวกัน มีหลักฐานว่าเว็บและ Edge Function บน staging ทำงานจริง การที่ HTTP ตอบว่าเข้าคิวแล้วหรือการที่ทดสอบผ่านในเครื่องไม่พอ ถ้ารายงาน MathQuest ยังไม่แสดงสรุปยอดตาม revision ให้เพิ่มสรุปจาก ACK ที่บันทึก ไม่ใช้จำนวนแถวคะแนนสะสมแทน การส่งรอบใหม่ที่ละบางรหัสไว้ไม่ใช่การถอนคะแนนเดิม

## 3. งานระยะ B: สัญญาขอเชื่อมแบบไม่ใช้รหัส

ใช้ `POST /functions/v1/pair-scansob-workspace` ฝั่ง MathQuest เดิม ไม่เปลี่ยนสัญญาคะแนน 1.0 หรือ endpoint ส่งคะแนน เพิ่มเฉพาะการเตรียมและส่งคำขอแบบลงนาม ฝั่ง ScanSob ยังต้องใช้ `status` และ `revoke` เดิมสำหรับกู้คำขอ ให้สองทีมยืนยันชื่อฟิลด์และไฟล์ fixture ร่วมกันก่อนแก้ strict schema

| การเรียก | ข้อเสนอที่ส่งให้ทีม ScanSob ยืนยัน |
| --- | --- |
| **`prepare_signed`** | ScanSob Backend ตรวจผู้ใช้ที่อนุมัติแล้วและเป็นเจ้าของ Workspace ดึงตัวตนที่ตรวจแล้วจาก Auth/DB แล้วลงนามคำขอที่มี `request_id`, `source_workspace_id`, `destination_school_id`, `sender_auth_id`, `sender_verified_email` MathQuest ตรวจลายเซ็น ปลายทาง รายชื่อ และสถานะเปิดรับ ก่อนตอบข้อมูลที่มี `request_id`, `destination_school_id`, `pairing_window_id` ยังไม่สร้าง pending และไม่คืน token ส่งคะแนน |
| **`request_signed`** | เพิ่ม `pairing_window_id` ใน body ตาม Handoff เดิม ลงนามครอบคลุม body ที่ส่งจริงทั้งหมด Server MathQuest ตรวจว่า window ตรงกับรอบที่เปิดอยู่ก่อนบันทึกคำขอใหม่ UUID มาจาก backend หรือค่าที่กำหนดบน server ไม่รับ School/URL/อีเมลที่กรอกเองจาก Browser มาเป็นหลักฐาน |
| **`status`** | ใช้ request ID, Workspace และ challenge ที่ผูกกับคำขอเดิม ตรวจว่า ACK ตรง ID และเมื่อได้ `active` ต้องตรวจ `destination_school_id` กับปลายทางที่ตั้งไว้ก่อนเข้ารหัสและเก็บ token ตรวจสถานะอัตโนมัติในหน้ารอโดยคุมความถี่และหยุดเมื่อเปลี่ยน Workspace หรือออกจากหน้า |
| **`revoke`** | ยกเลิกคำขอด้วยข้อมูลที่ผูกกับ ID เดิม ไม่เคลียร์สถานะหรือสร้าง ID ใหม่จนยืนยัน revoke ACK ตามสัญญาเดิม `expired` อาจหมายถึงเลยเวลารับ token หลังอนุมัติ ไม่ใช่หลักฐานว่าปลายทางไม่เคยเปิด connection |

- **รอบเปิดรับ:** MathQuest สร้าง UUID ใหม่เมื่อเปิดรับรอบใหม่ ล้างรอบเมื่อปิดรับหรือรีเซ็ตเทอม `pairing_window_id` เป็นตัวระบุรอบ ไม่ใช่สิทธิ์อนุมัติหรือ token ส่งคะแนน การตรวจอายุของลายเซ็นยังอยู่ แต่ไม่เอาเวลาที่ ScanSob สร้างคำขอมาใช้แทน ID รอบ
- **กู้คำขอเมื่อเน็ตหลุด:** ScanSob เก็บ attempt, request ID, challenge และ body เดิมในที่เก็บฝั่ง server ก่อนส่ง ถ้าผลไม่แน่ชัด ให้ลองส่ง body เดิมซ้ำก่อน `status` เพราะตัวรับเดิมอาจปิด ID ที่ไม่เคยถูกบันทึกเมื่อมีการเช็กสถานะ ห้ามขอ window ใหม่มาใส่ใน attempt เดิม หากยืนยันรอบไม่ได้หรือหมดรอบ ให้แสดงผลและให้ครูเริ่มคำขอใหม่เองหลังปิด attempt เดิมอย่างปลอดภัย
- **กติกากันซ้ำ:** คำขอใช้รหัสและแบบลงนามใช้กติกาเดียวกัน ให้มี pending ที่ยังไม่หมดอายุหรือ active ได้ไม่เกินหนึ่งรายการต่อโรงเรียนปลายทาง + Workspace ตรวจในธุรกรรมก่อนใช้รหัสหรือสร้างรายการ การส่งซ้ำด้วย ID และ body เดิมยังต้องตรวจผลเดิมได้ ไม่ให้รอบเปิดรับใหม่ชุบชีวิต ID เดิม
- **การตอบกลับ:** คำขอที่ commit แล้วคืน ACK ตามรูปแบบเดิม; `pending_approval`, `rejected`, `expired` ไม่มี token ข้อเสนอ error ใหม่คือ `PAIRING_WINDOW_CHANGED` (รอบเปลี่ยน) และ `PAIRING_WORKSPACE_BUSY` (มี pending/active) ให้ตกลง HTTP status และข้อความบน UI ร่วมกันก่อนพัฒนา ห้ามเปลี่ยนเป็น flow ใช้รหัสหรือสรุปว่ายกเลิกสำเร็จเงียบ ๆ เมื่อพบ error หรือ timeout

## 4. สิ่งที่แต่ละฝั่งต้องส่งมอบในระยะ B

### ScanSob

1. ปุ่ม **ส่งคำขอเชื่อมต่อ** ในหน้าเชื่อม MathQuest แสดงปลายทาง ชื่อ Workspace และขอบเขตส่งคะแนนเดิม แสดงเฉพาะเมื่อ backend ตรวจว่าปลายทางรองรับและเปิดรับ ผู้ไม่มีสิทธิ์ต้องไม่ส่งผ่าน API ได้
2. ตัวส่งจาก server รองรับ prepare/sign/submit และเก็บข้อมูล retry แบบ server-only ตรวจสิทธิ์เจ้าของ อีเมลที่ยืนยัน และปลายทางทุกขั้นที่เกี่ยวข้อง อย่าส่ง secret, challenge หรือ token กลับ Browser
3. หน้าตามสถานะจริง: **กำลังส่ง / ยังยืนยันผลไม่ได้ / รออนุมัติ / เชื่อมต่อแล้ว / ปฏิเสธ / หมดอายุ / ยกเลิกแล้ว** เชื่อมต่อแล้วได้หลังบันทึก token เท่านั้น คง manual send, preview และ publisher เดิม ไม่ย้ายสิทธิ์ข้าม Workspace
4. แยกค่าเปิดรับคำขอแบบใหม่จาก flag ส่งคะแนนเดิม หากปิดโหมดใหม่ ต้องยังตรวจและยกเลิกคำขอที่ค้างได้ และยังใช้ connection เดิมได้

### MathQuest

1. ปรับร่าง migration และ Edge Function ให้รองรับ window ID และกติกากันซ้ำทั้งสองทาง ครอบคลุมการชนกันระหว่าง approve/reject/revoke/expire ตรวจอีเมลและสิทธิ์อีกครั้งในธุรกรรมอนุมัติ
2. ใช้ inbox เดิมที่ทำไว้ผ่าน teacher session ตรวจว่าใช้ Realtime ช่องส่วนตัว ส่งเฉพาะสัญญาณ ไม่ส่งรายละเอียดผู้ขอในช่องนี้ และ polling ทำให้ครูยังเห็นผลเมื่อ Realtime ไม่พร้อม กดอ่านไม่ลด badge ลดเฉพาะเมื่อคำขอออกจากคิวรอ
3. เก็บ audit ผู้ส่ง Workspace ผู้ตัดสิน เวลา และผล เลือกปิดรับคำขอใหม่แยกจากรับคะแนน ปิดทางใหม่หรือ deploy แล้วต้องไม่เปลี่ยน token เก่า ไม่เผยคะแนนย้อนหลัง และไม่ลบแทนการถอนคะแนน

## 5. ค่าตั้งและสิ่งที่จะส่งกลับ

| จุดตั้ง | เฉพาะชื่อ/รูปแบบ ห้ามแชร์ค่าจริง |
| --- | --- |
| **ScanSob Netlify / server** | `MATHQUEST_RECEIVER_ORIGIN`: HTTPS origin ของ Supabase MathQuest ไม่ต่อ path; `MATHQUEST_DESTINATION_SCHOOL_ID`: UUID โรงเรียนในตัวรับ ไม่ใช่ project ref; `SCORE_INTEGRATION_ENABLED`, `MATHQUEST_RECEIVER_VERIFIED`: boolean เดิม; flag สำหรับเริ่มแบบใหม่ เช่น `MATHQUEST_CODE_FREE_PAIRING_ENABLED`; signing key และ key ID ฝั่ง server ตามที่ตกลง |
| **MathQuest Supabase / Edge Function Secrets** | คง `SCANSOB_PAIRING_DELIVERY_KEY` เดิม; ค่าที่ร่างอ่านคือ `SCANSOB_CODE_FREE_SIGNING_KEY` (32 ไบต์ base64url แบบไม่มี padding), `SCANSOB_CODE_FREE_SIGNING_KEY_ID`, `SCANSOB_CODE_FREE_DESTINATION_ID`; แยกชุด staging กับ Production และไม่แลก Supabase service key |

ก่อนพัฒนาระยะ B ให้ทีม ScanSob ส่งกลับ **(1)** commit และ staging ที่จะใช้ทดสอบระยะ A **(2)** การยืนยันหรือข้อแก้ไขสัญญา `prepare_signed` / `request_signed` / recovery **(3)** แผน rollout กับรายชื่อ migration ฝั่งตน เมื่อทดสอบเสร็จส่ง **PR/commit + เวอร์ชัน staging ทั้งสองฝั่ง + ผลตรวจรับที่ปิดบังข้อมูลนักเรียนและความลับ** ให้กัน

**เกณฑ์เปิดใช้จริง:** A ผ่านบน staging ก่อน แล้ว B ต้องผ่านตั้งแต่ขอเชื่อมแบบไม่ใช้รหัสจนถึงกดส่งและถอนคะแนนจำลอง ตรวจด้วยว่าคำขอผิดปลายทาง ไม่มีสิทธิ์ คนละรอบ หรือลงพร้อมกันสองวิธีไม่สร้างรายการซ้ำ และครูที่ไม่ได้เป็นแอดมิน/นักเรียนอ่าน inbox ไม่ได้ เปิดทีละกลุ่มหลังได้รับอนุมัติ คงการจับคู่เดิมเป็นทางสำรองช่วงเปลี่ยนผ่าน
